# AV Derivative Provenance

## Goal

AV Derivative Provenance is a backend for media engineering teams that need a
deterministic way to derive smaller audio or video outputs and later prove how
those outputs were made. It accepts PCM WAV audio and Y4M frame streams,
records every source and result by digest, applies an explicit operation
plan, and replays that plan when an integrity check is requested.

The application does not depend on external media binaries. Its value is the
combination of byte-level media processing with durable provenance and a
reproduction check that compares freshly generated bytes against the stored
result.

## Users

- Media pipeline engineers who need to transform bounded source clips without
  adding a native media dependency.
- Quality engineers who need proof that a derivative can be recreated from
  recorded inputs and operations.
- Platform engineers who need a compact HTTP boundary around media processing,
  durable state, and lineage.

## Project shape

- Shape: `backend`
- Language: Python 3.11+
- Runtime: Python standard runtime only
- Persistence: JSON state plus content-addressed binary files below one data
  directory
- Public boundary: HTTP/JSON
- Input media: PCM WAV and planar YUV4MPEG2 in the `C420` family
- Output media: PCM WAV and planar YUV4MPEG2 in the `C420` family

## Core entities

### Media asset

An immutable source blob with a server identifier, original filename, media
kind, SHA-256 digest, size, content key, inspected descriptor, and creation
time. Reusing the same bytes creates a distinct asset identifier while
sharing the content-addressed blob.

Invariants:

- The stored length and digest must match the advertised bytes.
- The media descriptor must be derived from the stored bytes.
- An asset never changes after creation.
- A source is not persisted unless its bytes pass media inspection.

### Rendition

A request to derive one output from a primary asset, an optional secondary
asset, and a sequenced operation plan.

Fields include the primary and secondary asset identifiers, normalized
operations, plan digest, lifecycle status, transition history, output asset
identifier, failure detail, and timestamps.

### Provenance edge

An immutable record linking a completed rendition to its parent asset
identifiers, operation plan digest, and output asset identifier.

Invariants:

- Exactly one provenance edge exists for a completed rendition.
- Parent identifiers in the edge equal the rendition parent identifiers.
- The output asset exists and its digest is recorded.

### Integrity check

A persisted attempt to reproduce a completed rendition from its parents and
plan. Its states are `pending`, `verified`, and `mismatch`.

Fields include the rendition identifier, expected output digest, reproduced
digest, result, reason, and check time.

## State machines

### Rendition lifecycle

```text
queued -> running -> completed
                  \-> failed
```

Rules:

- A rendition is persisted as `queued` before execution begins.
- The transition to `running` is written before media operations start.
- Success adds the output asset and provenance edge before exposing
  `completed`.
- Failure records a stable error code and does not create a provenance edge.
- Terminal states cannot transition again.

### Integrity check lifecycle

```text
pending -> verified
        \-> mismatch
```

Rules:

- A check is persisted as `pending` before reproduction starts.
- `verified` requires equal media descriptors and equal SHA-256 output bytes.
- Any missing parent, plan drift, missing output, or byte difference yields
  `mismatch` with a stable reason.

## Workflows

### 1. Ingest media asset

Entry point: `POST /v1/assets`

Steps:

1. The HTTP boundary validates request size and base64 shape.
2. The application validates the filename and decoded byte budget.
3. The media inspector identifies and probes WAV or Y4M bytes.
4. The blob repository writes the content-addressed source.
5. The repository commits the immutable asset record.
6. The HTTP boundary returns the public asset representation.

Success:

- Returns `201` with asset identifier, digest, size, and media descriptor.
- A following `GET /v1/assets/{asset_id}` returns the same metadata.

Failure:

- Invalid or empty content returns `400 VALIDATION_ERROR`.
- Unknown or malformed media returns `415 UNSUPPORTED_MEDIA`.
- A persistence failure removes any newly written orphan blob when safe.

### 2. Execute rendition

Entry point: `POST /v1/renditions`

Steps:

1. The HTTP boundary reads the plan and output filename.
2. The plan compiler checks the primary media kind, secondary usage, and
   operation-specific parameters.
3. The repository persists a `queued` rendition.
4. The application records `running` and reads parent media bytes.
5. The executor applies audio or video operations in sequence.
6. The result is inspected, hashed, and saved as a new derivative asset.
7. The repository appends a provenance edge.
8. The rendition transitions to `completed`.

Success:

- Returns `201` with a completed rendition representation.
- The representation includes transition history, normalized operations,
  plan digest, and output asset identifier.

Failure:

- Invalid plans return `422 PLAN_INVALID`.
- Missing assets return `404 ASSET_NOT_FOUND`.
- Processing failure records `failed` with `RENDER_FAILED` and returns a stable
  error body. No completed output edge is emitted.

### 3. Verify reproduction

Entry point: `POST /v1/renditions/{rendition_id}/integrity-checks`

Steps:

1. The application loads a completed rendition and its provenance edge.
2. The verifier loads both parent assets and the recorded output.
3. Every parent blob is re-read in full and its SHA-256 compared with the
   immutable asset record before any replay (`source_digest_drift` on failure).
4. The verifier loads the recorded output and confirms its digest as well.
5. The executor repeats the stored normalized plan as a full replay.
6. The verifier compares reproduced bytes and media descriptors with the
   recorded output.
7. The repository persists the integrity result.
8. The HTTP boundary returns the result.

Success:

- Returns `201` with `result: "verified"` and matching digests.

Failure:

- A completed rendition must exist, otherwise `404`.
- Parent or output loss yields `mismatch`.
- Whole-source digest drift, replay digest, or descriptor drift yields
  `409 INTEGRITY_MISMATCH` while retaining the persisted mismatch check.

### Ranged local reads

Renditions whose normalized plan starts with `media_trim` and whose remaining
operations are all pointwise or window-local are served by a ranged read path
instead of loading the whole source:

- Eligibility is decided by `renditions/locality.py`. A secondary asset
  (`audio_mix`) or any whole-clip statistic computed before the trim
  (for example `audio_normalize` then `media_trim`) forces the full path.
- `storage/content_files.py` opens a seekable, byte-counted `FileMediaSource`;
  the blob is never fully buffered for an eligible rendition.
- The media module probes WAV/Y4M headers only and decodes the exact trim
  window via `wav.probe_wav`/`decode_wav_range` and
  `y4m.probe_y4m`/`decode_y4m_range`.
- Local and full paths share the same operation functions, so a local render
  is byte-identical to full execution. No decoded source content is cached.
- Any layout the ranged parser cannot prove equivalent raises
  `LocalReadUnavailable`; the application then runs the unchanged full
  read-and-decode path. Observable acceptance and error codes do not change.
- The ranged path only endorses bytes inside its window. Whole-source health
  remains the exclusive responsibility of the integrity check above.

## Supported media operations

Audio plans:

- `media_trim`: `start_seconds`, `duration_seconds`
- `audio_gain`: `db`
- `audio_normalize`: `target_peak`
- `audio_mix`: `secondary_gain`, `primary_weight`, `secondary_weight`

Video plans:

- `media_trim`: `start_frame`, `frame_count`
- `video_crop`: even `x`, `y`, `width`, `height`
- `video_luma_offset`: `amount`
- `video_mirror`: no additional parameters

All numeric bounds are validated before state is queued. Processing functions
also re-check data-dependent constraints so malformed persisted plans cannot
turn into partial output.

## Modules

| Module ID | Path | Responsibility |
| --- | --- | --- |
| `http_api` | `avprovenance/http_api.py` | HTTP routes, body limits, status mapping |
| `application` | `avprovenance/application.py` | Use-case orchestration, local/full routing, whole-source audits |
| `validation` | `avprovenance/validation.py` | Request and operation boundary checks |
| `media` | `avprovenance/media` | WAV/Y4M inspection, full and ranged byte operations |
| `renditions` | `avprovenance/renditions` | Plan normalization, locality analysis, execution, verification |
| `storage` | `avprovenance/storage` | Atomic state, ranged and full blob access, repository methods |

Dependency direction:

```text
http_api -> application -> renditions -> media
                       \-> storage
validation is called by http_api, application, and renditions
```

The media module does not import application or storage. The storage module
does not inspect media. The renditions module receives bytes and returns
outcomes without knowing HTTP details.

## Public HTTP interface

- `GET /health`
- `POST /v1/assets`
- `GET /v1/assets/{asset_id}`
- `POST /v1/renditions`
- `GET /v1/renditions/{rendition_id}`
- `GET /v1/renditions/{rendition_id}/lineage`
- `POST /v1/renditions/{rendition_id}/integrity-checks`

Every response is JSON. Errors contain `error.code`, `error.message`, and a
request identifier. Unexpected failures use `500 INTERNAL_ERROR` without
leaking local paths.

## Persistence and concurrency rules

- The state file is replaced atomically with `os.replace`.
- All repository mutations share a process-local re-entrant lock.
- Blob writes use a temporary sibling and atomic replacement.
- Content-addressed writes are idempotent.
- Blob paths are generated internally and cannot contain traversal segments.
- The HTTP server uses a threading server, while repository mutations remain
  serialized at the state boundary.

## Validation plan

The project intentionally defers automated tests to the later task stage.
Until that stage adds a verification suite, the following production workflow
checks are the baseline:

```bash
python3 -m compileall -q avprovenance scripts
python3 scripts/workflow_checks.py ingest-media-asset
python3 scripts/workflow_checks.py execute-rendition
python3 scripts/workflow_checks.py verify-reproduction
```

The checks start an ephemeral HTTP server, generate bounded media bytes in
memory, call the public endpoints, and assert observable state. They do not
require network access or external media programs.

## Intentionally omitted capabilities

- Native codec coverage beyond PCM WAV and planar Y4M.
- Persistent worker processes and cross-process task leases.
- Authentication and multi-tenant authorization.
- Object storage and distributed state.
- Automated tests, which belong to the later task stage.
